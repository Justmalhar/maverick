# Maverick Bug Hunt — Verified Report

_Triaged 47 confirmed findings down to 40 distinct bugs after merging duplicates (agent-cost-wipe reported twice; preset-launch contract-drift reported across three findings). Ordered by impact: (1) app-startup/core-feature breakage first — the Windows release-install sidecar path resolution that puts EVERY packaged Windows install into degraded mode is the single most severe issue; (2) Windows-specific feature breakage (media previews, skill parser, version probes, caffeinate); (3) data-loss and core git/kanban correctness bugs; (4) contract/wiring/resource-leak issues; (5) cosmetic no-ops and dead code. The preset-launch subsystem is structurally broken across several layers (worktree not persisted, PTY transport split, contract drift) and should be fixed holistically by choosing a single PTY authority. A recurring sidecar pattern — full-row SQLite upserts that NULL-out omitted fields — is the root cause of three separate kanban data-loss bugs and warrants a defense-in-depth fix in kanban-store.ts upsert._

## #1 [CRITICAL] Release sidecar path resolved one directory ABOVE the executable on Windows — every packaged install starts in permanent degraded mode

- **category:** windows-bug | **confidence:** high
- **files:** src-tauri/src/lib.rs
- **problem:** In release builds release_sidecar_command computes the sidecar path as resource_dir().parent().join("maverick-sidecar.exe"). Verified against Tauri 2.11.3 source: on Windows resource_dir() IS the directory containing the main executable, so .parent() walks one level ABOVE the install root and the computed path (e.g. C:\Program Files\maverick-sidecar.exe instead of C:\Program Files\Maverick\maverick-sidecar.exe) does not exist. Sidecar::spawn fails, lib.rs falls back to Sidecar::placeholder(), whose request() returns TransportClosed for everything. Result: EVERY sidecar-backed feature (projects, workspaces, git, diff, file tree, skills, agent, MCP, kanban, notifications) is dead on every Windows release install — the app silently runs degraded. The code comment ('puts the sidecar next to the main binary') contradicts the .parent() call. Debug builds use dev_sidecar_command and are unaffected, which is why it shipped untested. The same .parent() is also wrong on macOS (resource_dir=Contents/Resources, .parent()=Contents, binary is in Contents/MacOS).
- **fix:** Drop the .parent() call: resolve the sidecar in the same directory as resource_dir() on Windows (lines 99-104 in lib.rs). Most portable: use std::env::current_exe()?.parent() (correct on Windows, Linux, and macOS) or the tauri-plugin-shell sidecar() resolver (already a dependency) which accounts for the target-triple-renamed externalBin placement. Add a test constructing the expected path from a fixture exe dir, since release_sidecar_command currently has zero coverage.

## #2 [HIGH] Preset.launch creates a git worktree but never persists a workspace row — orphaned-worktree leak and lost workspace

- **category:** unwired | **confidence:** high
- **files:** sidecar/preset-launcher.ts, sidecar/rpc-handlers.ts, src/panels/presets/PresetPicker.tsx
- **problem:** PresetLauncher.launch() calls worktree.create() (which runs git worktree add, creating a real on-disk worktree and branch) and spawns PTYs, but NEVER calls store.workspaceCreate() to persist a Workspace row — despite the store being injected. Consequences: (a) workspace.destroy() short-circuits at `if (!ws) return {ok:true}` (rpc-handlers.ts:573-574) so worktree.destroy() is never called and the worktree dir leaks on disk forever; (b) after restart workspace.list reads the DB and the workspace is permanently lost; (c) PTYs spawned during traverse() are keyed by a workspaceId with no DB row and no kill path, leaking for the sidecar lifetime. PresetPicker.tsx papers over this with an in-memory Zustand row using worktreePath:'' that is never written back to the DB.
- **fix:** After worktree.create succeeds in launch(), call store?.workspaceCreate({ id: workspaceId, projectId, branch: presetBranch, agentBackend: 'preset', worktreePath, title: preset.name }). Thread projectId into LaunchParams by resolving it in the preset.launch RPC handler (rpc-handlers.ts:875-882) via store.projectByPath(p.projectPath)?.id (preset.list already does this). workspaceCreate honors an explicit id so the spawned PTYs' key stays consistent.

## #3 [HIGH] Preset-launched terminals use a separate sidecar pipe-based PTY registry the frontend can never display, drive, or kill (split PTY authority)

- **category:** unwired | **confidence:** high
- **files:** sidecar/process-manager.ts, sidecar/preset-launcher.ts, src/panels/presets/PresetPicker.tsx, src-tauri/src/commands/pty.rs, sidecar/rpc-handlers.ts
- **problem:** Two incompatible PTY backends exist. Normal terminal/agent tabs use the Tauri pty_spawn -> Rust ConPTY PtyManager (real PTY). But preset.launch goes through the sidecar's ProcessManager.spawn = Bun.spawn with stdout/stderr pipes (NOT a PTY), keyed in a separate Map with uuid ids. The frontend's pty_write/resize/kill target the Rust PtyManager registry, which has no record of the sidecar's uuid ptyIds, so any write/resize/kill against a preset ptyId fails with 'PTY not found'. The sidecar's pty.spawn/write/resize/kill dispatch cases (rpc-handlers.ts:625-644, including the documented cwd->worktreePath default) are unreachable dead code since nothing sends pty.* JSON-RPC. Net effect: launching a preset spawns real child processes that are headless (no ConPTY -> CLI sees non-TTY and disables interactive UI), undriveable, and leaked. Merges three findings (split registry, dead sidecar pty dispatch, and resize/workspaceId no-ops).
- **fix:** Pick one PTY authority. Preferred: make preset.launch return a layout descriptor (PresetNode tree + per-terminal cwd/command + browserPanes) WITHOUT pre-spawning, and have the frontend build the SplitGrid and spawn each terminal node via the existing Rust ptySpawn (ConPTY) path — reusing the proven TerminalLeaf/usePty machinery and automatic Rust kill lifecycle. This also makes the documented worktree-cwd default live (it must exist on whichever path survives). If sidecar spawning is kept instead, route write/resize/kill through sidecar JSON-RPC, replace Bun.spawn pipes with a real PTY, add a ProcessManager.killWorkspace(workspaceId) called from workspace.destroy, and remove the dead resize/cols/rows fields.

## #5 [HIGH] Preset.launch base branch hardcodes 'main' with no resolveBaseBranch fallback — hard-fails on master-only / origin-only repos

- **category:** logic-bug | **confidence:** high
- **files:** sidecar/preset-launcher.ts
- **problem:** launch() computes branch = preset.baseBranch ?? params.baseBranch ?? 'main' and passes it to worktree.create as baseBranch, running `git worktree add -b <new> <path> main` with NO ref verification. Unlike workspace.create (rpc-handlers.ts:541-547) which routes candidates through worktree.resolveBaseBranch ending in a guaranteed HEAD fallback, preset.launch does no resolution. On a repo whose default branch is master, or a fresh clone where only origin/main exists locally, the worktree add exits non-zero and create() throws a raw git error — the preset launch fails entirely with no recovery, even though resolveBaseBranch was built for exactly this and is available on the injected manager.
- **fix:** Resolve the base ref before create: const baseBranch = await this.worktree.resolveBaseBranch(params.projectPath, [params.preset.baseBranch, params.baseBranch, 'origin/main', 'main', 'master']); and pass that as baseBranch, mirroring workspace.create. resolveBaseBranch falls back to HEAD so the bare/no-main/no-master case is also fixed. Add a test injecting a worktree mock whose resolveBaseBranch is invoked with the candidate list.

## #10 [HIGH] Checking out a remote branch detaches HEAD — checkoutBranch never strips the remote because branchList already removed the 'remotes/' prefix

- **category:** contract-mismatch | **confidence:** high
- **files:** sidecar/git-module.ts
- **problem:** parseBranches strips both refs/heads/ and refs/remotes/, so a remote branch reaches the UI as name='origin/feat' (isRemote:true). BranchList passes that verbatim to gitCheckout -> checkoutBranch({branch:'origin/feat'}). checkoutBranch (git-module.ts:268-273) only strips a literal 'remotes/' prefix, which is FALSE for 'origin/feat', so it runs `git checkout origin/feat` — checking out the remote-tracking ref directly and producing a DETACHED HEAD instead of a local tracking branch. Empirically reproduced: `git checkout origin/feat` => detached HEAD, while `git checkout feat` DWIMs to a tracking branch. The doc comment claims it strips the remote to auto-create a tracking branch — it does the opposite. The passing unit test feeds synthetic 'remotes/origin/feat' which the real flow never produces.
- **fix:** Normalize a remote-tracking name to its short branch name. Robust form: thread isRemote/upstream through and emit an explicit `git checkout -b <local> --track <remote>/<branch>` for remote rows. Minimal: const stripped = params.branch.replace(/^remotes\//, ''); const ref = stripped.includes('/') ? stripped.slice(stripped.indexOf('/')+1) : stripped; (caveat: bare first-slice mishandles multi-remote ambiguity and slash-containing branch names like feature/foo). Fix the misleading test at git-module.test.ts:418 to use real 'origin/feat' input.

## #11 [HIGH] GitHub compare-URL fallback percent-encodes the slash in slash-prefixed branch names — broken 404 compare URL

- **category:** logic-bug | **confidence:** high
- **files:** sidecar/git-provider.ts
- **problem:** prWebUrl builds the GitHub compare fallback as `${webUrl}/compare/${encodeURIComponent(baseRef)}...${encodeURIComponent(branch)}?expand=1` (line 67). The refs live in the URL PATH but encodeURIComponent encodes '/' as '%2F'. GitHub routes compare refs by literal '/' segments, so a head ref like 'feature/login-page' must appear literally; encoded as 'feature%2Flogin-page' GitHub treats it as a single non-existent ref and the compare page fails. This is exactly the path taken when gh is not installed/authenticated (git-module.ts:498/504) — the headline 'open a PR' feature for users without gh, common on this Windows-first port. Slash branches are the dominant shape (the AI branch-name generator deliberately preserves slash prefixes). Existing tests use slashless 'feat' so they pass.
- **fix:** Encode each path segment but preserve the slash: const enc = (r) => r.split('/').map(encodeURIComponent).join('/'); then `.../compare/${enc(baseRef)}...${enc(branch)}?expand=1`. Leave the bitbucket source= and gitlab merge_request[source_branch]= cases unchanged (those are query-param values where %2F decodes correctly server-side). Add a regression test for prWebUrl(gh, 'feature/login-page').

## #14 [HIGH] claude -p AI calls have no sidecar-side timeout/kill — orphaned subprocess + whole-sidecar stall on hang

- **category:** resource-leak | **confidence:** high
- **files:** sidecar/commit-message.ts, sidecar/branch-name-generator.ts, sidecar/deps.ts, sidecar/index.ts
- **problem:** CommitMessageGenerator.generate and BranchNameGenerator.generate/generateFromDiff call this.shell.run(['claude','-p',...]) with NO internal timeout and NO kill. defaultShell.run unconditionally awaits proc.exited with no abort path. When claude -p hangs (not logged in/blocking, network stall, slow cold start), the Rust transport times out (180s commit_message, 60s branch_name) and merely removes the pending oneshot — it sends NOTHING to the sidecar, so the claude child keeps running as an orphan holding open pipes. Worse: index.ts processes RPC lines strictly serially (for await ... await processLine), so while generate() is blocked the ENTIRE sidecar is blocked — git status, file reads, diff, kanban all queue behind it and the UI appears frozen. The author already mitigates this elsewhere (workspace.destroy races a spawn against a 30s timer and kills the child).
- **fix:** Add a bounded killing timeout to the AI shell calls: extend Shell.run with an AbortSignal/timeoutMs and race proc.exited against a timer that calls proc.kill() on expiry (or use the spawnOnceHandle race pattern already in workspace.destroy). Budget should be shorter than the Rust transport timeout (~150s commit, ~45s branch) so the child is reaped before Rust gives up. Separately, avoid awaiting long LLM dispatches inside the serial line loop so one slow AI call cannot stall unrelated RPCs.

## #15 [HIGH] stderr pipe of every ProcessManager-spawned child is never drained — child deadlocks once the ~64KB stderr buffer fills

- **category:** resource-leak | **confidence:** high
- **files:** sidecar/process-manager.ts
- **problem:** defaultSpawner sets stderr:'pipe' (line 19) but pumpStdout only reads proc.stdout (lines 117-134); proc.stderr is never read. Any child (preset terminal agent/shell, or the workspace.destroy archive script) that writes more than the OS pipe buffer (~64KB) to stderr blocks on its next stderr write and hangs forever. The preset-terminal path has NO timeout guard. All stderr diagnostics are also lost (never surfaced as pty.data/pty.error). The author clearly knows stderr must be drained — agent-runner.ts and mcp-manager.ts both pump proc.stderr; ProcessManager is the lone outlier.
- **fix:** In pumpStdout also drain proc.stderr concurrently (mirror agent-runner.ts): build pumps for stdout and stderr, Promise.all them before awaiting proc.exited, and emit stderr chunks as pty.data so diagnostics are visible. For the spawnOnceHandle/archive path, drain stderr or switch that spawn to stderr:'inherit'. Add a regression test writing >64KB to stderr and asserting it exits rather than hanging.

## #16 [HIGH] ProcessManager.write never flushes Bun's buffered stdin sink — interactive input may never reach the child

- **category:** logic-bug | **confidence:** high
- **files:** sidecar/process-manager.ts, sidecar/preset-launcher.ts
- **problem:** write() (lines 68-74) calls entry.proc.stdin.write(data) and returns, never calling flush(). Bun.spawn's stdin is a buffered FileSink: write() enqueues into an internal buffer and the bytes are not pushed to the OS pipe until .flush() or close. For interactive terminal input (single keystrokes, the PresetLauncher startup line node.startup+'\n'), small writes sit in the buffer and never reach the agent/shell. The ManagedProc.stdin interface even declares flush?() (line 6), signalling the author knew it was needed. The two other stdin-write sites (deps.ts, agent-runner.ts) call .end() right after write (which flushes); only this keep-stdin-open path is missing flush.
- **fix:** After the write, call await entry.proc.stdin.flush?.() (guard the optional method for test fakes). Add a test asserting flush() is invoked after write(). Longer term the correct mechanism for an interactive PTY is Bun's terminal:/ConPTY option rather than stdin:'pipe', but the minimal fix is the flush() call.

## #20 [MEDIUM] resolveConflict ignores hunkIndex and resolves the WHOLE file, breaking per-hunk Accept Ours/Theirs
